<gap_source>
From `10-VERIFICATION.md` gaps:
- Truth failed: "User configuration changes save and reload deterministically when app saves and external edits occur in close timing windows."
- Reason: `ApplyWatcherAsync` computes the current file hash before entering the reload read/failure path. If `ComputeHashAsync` throws during an external writer-lock race, the operation-loop catch only logs and drops the watcher operation.
- Missing: catch hash/read exceptions inside `ApplyWatcherAsync` (or route hashing through `ReadForReloadAsync`) and publish a typed `Watcher`/`ReadFailed` result/failure; add deterministic coverage where `ComputeHashAsync` throws once and a later valid watcher reload still succeeds.
</gap_source>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| External settings file → configuration coordinator | Untrusted filesystem content and file-lock/read failures enter via watcher-triggered reads. |
| Coordinator queue → observers/ViewModels | Typed results/failures cross from background service logic to UI-facing consumers. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-10-01 | D | `ConfigPersistenceCoordinator.ApplyWatcherAsync` | mitigate | Catch non-cancellation hash-read exceptions and publish a typed failed watcher result so transient external writer locks do not silently drop reload work. |
| T-10-10-02 | I | `ConfigPersistenceFailure` from watcher hash path | mitigate | Use existing safe summary `Could not read settings file (read_failed)` and do not expose raw exception objects to observers/ViewModels per D-28. |
| T-10-10-03 | T | Later watcher reload after transient failure | mitigate | Regression proves the coordinator loop remains alive and later valid content is accepted through normal validation before state mutation. |
</threat_model>
